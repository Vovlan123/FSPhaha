# Plan.md: ФСП Талант — MVP платформы подбора ИТ-специалистов

Дата актуализации: 2026-10-11

## Цель

Собрать работающий MVP с двумя кабинетами: кандидата и работодателя. Сквозной сценарий проходит без ручных обходов:

1. Регистрация соискателя.
2. Опрос, выбор грейда, адаптивный тест.
3. Присвоение категории.
4. Работодатель описывает потребность и получает объяснённую подборку.
5. Работодатель приглашает кандидата с зарплатной вилкой.
6. Кандидат принимает приглашение, контакты раскрываются.

К MVP прилагаются валидация с цифрами и документация, достаточные для промежуточной и финальной сдачи.

## Постоянный контекст

- `spec.md` — требования, сущности, статусы, формулы механик.
- `docs/approach.md` — краткое описание подхода (для промежуточной сдачи).
- `README.md` — стек, запуск, демо-аккаунты.
- `plan.md` — состояние плана, активный шаг, допущения.

## Границы

Входит:

- JWT-авторизация с подтверждением email, роли `candidate` и `employer`;
- профиль кандидата: заполнение формой или из PDF, генерация PDF-профиля;
- опрос, выбор грейда, адаптивный тест на параметрических шаблонах с IRT, ограничения частоты, детектор утечек;
- подборка по потребности с ранжированием, объяснениями, шорт-листом и фильтрами без потери подборки;
- банк кандидатов с фильтрами;
- приглашения со статусами и раскрытием контактов;
- вакансии и отклики;
- регулярные задания с рубрикой;
- mock-реестр ФСП с OAuth-потоком в формате Keycloak;
- скрипт валидации с отчётом;
- `docker-compose.yml`, OpenAPI, README.

Не входит:

- реальный Keycloak и реальный реестр ФСП;
- LLM в рантайме;
- исполнение кода кандидата на сервере;
- модерация, верификация компаний, интеграция с ATS — только концепция в документации;
- чат внутри платформы;
- мобильные приложения.

## Допущения и вопросы

- На машине разработки нет Docker. Поэтому основной режим локального запуска — Python + Node + SQLite. `docker-compose.yml` с PostgreSQL готовится, но на этой машине не проверяется — допущение.
- Справочник: 5 специализаций × 4 грейда, пороги θ из `spec.md` — допущение команды.
- Параметры IRT шаблонов заданы экспертно. Их корректность проверяется восстановлением на синтетике — допущение.
- Срок хакатона и состав команды неизвестны. План рассчитан на последовательное выполнение одним агентом — вопрос к пользователю.
- Брендбук ФСП не приложен. Используется фиолетовая гамма с титульной страницы ТЗ — допущение.

## Слои

### `frontend`

Зона ответственности:

- SPA на React для обеих ролей с маршрутизацией по ролям;
- онбординг-мастер кандидата, экран теста, экраны результата и статуса;
- экраны подборки, банка, карточки кандидата, приглашений, вакансий, заданий;
- пустые и ошибочные состояния, обязательная вилка в формах.

### `backend`

Зона ответственности:

- REST API с OpenAPI;
- проверка ролей и правил видимости;
- движок тестирования: банк шаблонов, IRT, CAT, решение по грейду, ограничения частоты, детектор утечек;
- подбор: NLP-разбор, сила профиля, балл соответствия, причины;
- OAuth-клиент к реестру ФСП;
- разбор и генерация PDF;
- отправка писем.

### `database`

Зона ответственности:

- модели SQLAlchemy по сущностям `spec.md`;
- SQLite локально, PostgreSQL в Docker;
- генератор тестовых данных: 300+ кандидатов через настоящий движок тестов, компании, потребности, вакансии, приглашения, задания.

## Критерии готовности

- Новый кандидат проходит путь «регистрация → подтверждение email → профиль → опрос → грейд → тест → категория» без ручных обходов.
- Работодатель по текстовому описанию потребности получает подборку с баллом и причинами у каждого кандидата.
- Приглашение невозможно отправить без вилки «от–до» в рублях.
- Контакты кандидата не приходят в ответах API работодателю до принятия приглашения или отклика.
- `correct_index` не приходит в ответах API кандидату.
- Профиль без истории ФСП отображается без ошибок, с понятной плашкой.
- Отчёт валидации содержит метрики теста и подбора со сравнением с бейзлайнами.
- OpenAPI доступен по `/docs`, копия лежит в `docs/openapi.json`.
